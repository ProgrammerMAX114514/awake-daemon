# Review workflow (two-account setup)

This project uses two GitHub accounts on purpose. The point is to make "someone reviewed this" a fact that GitHub enforces, not a habit.

## The two accounts

| Account | Role | Permissions | Authenticates with |
| --- | --- | --- | --- |
| `ProgrammerMAX114514` | Author: writes code, signs commits (GPG), opens pull requests, merges after approval | owner (`admin`) | `gh` login on the keyring; pushes go through Windows Git Credential Manager so commits stay GPG signed by this account |
| `BuddyPRReviewer` | Reviewer: reads the diff, leaves review comments, submits the approving review | collaborator, `role_name: write` | a personal access token passed as `GH_TOKEN` in the review session |

GitHub refuses to let an account approve its own pull request. The rule is evaluated per account, not per person or per device, so a second account is the supported way to have an approval that the branch protection rule actually counts.

## Branch protection on `main`

| Setting | Value | Effect |
| --- | --- | --- |
| `required_approving_review_count` | `1` | At least one approving review is required |
| `require_code_owner_reviews` | `true` | The approval must come from a code owner listed in `.github/CODEOWNERS` |
| `dismiss_stale_reviews` | `true` | A new commit on the branch invalidates earlier approvals |
| `require_last_push_approval` | `true` | The approval must not come from whoever pushed the branch last |
| `enforce_admins` | `true` | The owner account cannot merge its own pull request either |
| `required_status_checks` | `Build and smoke test`, `Static analysis (/analyze)`, strict | CI must be green and the branch must be up to date with `main` |
| `allow_force_pushes` / `allow_deletions` | `false` | No force pushes, no branch deletion |

`strict = true` means the branch has to contain the current `main`, so CI re-runs against the merge result rather than against the branch head.

## The review session

The reviewer session authenticates with the reviewer account through an environment variable. `GH_TOKEN` takes priority over the local `gh` login, so the author session keeps its own login state and its GPG signing key untouched.

```sh
export GH_TOKEN=<reviewer-account-token>
```

The token is never stored in the repository, in the workflows or in this document: the review session reads it from wherever the operator keeps it and passes it only through the environment.

Read the pull request and its checks:

```sh
gh pr view <number> --json title,body,files,statusCheckRollup
gh pr diff <number>
gh pr checks <number>
```

Leave a review comment:

```sh
gh pr review <number> --comment --body "..."
```

Approve (only once the review is actually satisfactory):

```sh
gh pr review <number> --approve --body "..."
```

GitHub does not allow both `--comment` and `--approve` in one request. Send them as two separate calls if the review needs both a comment and an approval.

## Rules for the reviewer session

- Never run `gh auth setup-git`. The repository relies on the Windows Git Credential Manager for pushes so that commits are signed by the author account's GPG key. Replacing the credential helper with `gh` switches pushes to the reviewer account and breaks the signing chain.
- Never push from the reviewer session. The reviewer account exists to review, not to author.
- Every review comment must disclose that an AI assistant wrote it, on the first line or in a clearly visible position, for example:

  ```text
  > **This review was generated by an AI assistant.**
  ```

- The reviewer does not merge. The author account merges after the approval lands and CI is green.

## How a change flows through

1. The author session creates a branch, commits with GPG signing, and pushes.
2. The author session opens the pull request with `gh pr create`.
3. CI runs. `Build and smoke test` and `Static analysis (/analyze)` must both pass.
4. GitHub requests a review from `@BuddyPRReviewer` automatically, because of `.github/CODEOWNERS`.
5. The review session reviews the diff and submits an approval (plus comments if needed).
6. If the author pushes another commit, the approval is dismissed automatically and the reviewer has to approve again.
7. The author session merges with a merge commit (`create a merge commit`, never squash or rebase, so the GPG signatures on the branch commits survive).

## First run

The pull request that introduced `.github/CODEOWNERS` was the first one to go through this gate, and it could not rely on the gate itself: `CODEOWNERS` only takes effect once it is on the default branch, so that pull request was approved manually - the reviewer account ran `gh pr review --approve` by hand in the review session, and the author account could not approve it because GitHub does not allow an account to approve its own pull request. Automatic review requests have applied to every pull request since.

## Troubleshooting

**The pull request says "Changes requested" but nobody requested changes.** Check `gh api repos/OWNER/REPO/pulls/NUMBER --jq .reviewDecision` and look at the reviews endpoint. A dismissed or stale approval shows up as `reviewDecision: null` while `mergeable_state` stays `blocked`.

**The merge button is greyed out even though the review was approved.** The approval is probably stale (the branch received a new commit afterwards) or the reviewer was the last one to push. `dismiss_stale_reviews` and `require_last_push_approval` both cause this on purpose.

**`gh` refuses to approve.** The running account is the author account. Check `gh auth status` and confirm `GH_TOKEN` is exported.

**The approval does not count.** `require_code_owner_reviews` is on, so the reviewer must be listed in `.github/CODEOWNERS` on the default branch. Verify the file is merged, not just open in a pull request.
