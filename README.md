## Features

- **Keep-awake** (`awake 1`): blocks *idle* sleep and hibernation only. Manual sleep via the power button, the Start menu, or sleep commands issued by other applications still works normally.
- **Screen keep-awake** (`awake screen on`): additionally keeps the screen on - blocks the display turning off, the screensaver and the lock screen caused by idle timeout.
- **Application watch list**: image names configured in `awake.ini`; while any of them is running, the daemon blocks idle sleep/hibernation the same way (checked every 30 seconds).
- **Power event awareness**: after the system resumes from sleep/hibernation, the daemon immediately re-applies the execution state and `awake status` shows when the last resume was handled.
- **Daemon autostart** (`awake daemon enable`): optionally starts the daemon automatically at logon (written to the per-user registry Run key, no admin rights needed).
- **Script-friendly output** (`awake list`, `--json`, `--no-color` / `NO_COLOR`): plain text and JSON modes for scripts and CI.
- **Status details**: `awake status` also shows the system power plan timeouts, the screensaver setting and which execution state requests the daemon holds.
- **Daemon logging** (`awake log`): rolling log files (enabled by default) in `%LOCALAPPDATA%\awake\logs\daemon` with configurable level and limits, and a one-command zip export (`awake log export`) for issue attachments.
- **Colored console output** via ANSI escape sequences.
- The client starts the daemon automatically when needed (for `awake 0` / `awake 1`).

## Build

Run `utils\build.bat` (from any directory). The batch file is a thin launcher for `utils\build.ps1`; the PowerShell script prepares the MSVC x64 environment (`utils\msvc-env.ps1`) and builds the Release configuration. It first tries the Visual Studio 2026 CMake generator and falls back to the NMake generator when that generator cannot run, so the executables are always written to:

```
build\Release\awake.exe
build\Release\awake.daemon.exe
```

Both executables statically link the C runtime and have no runtime dependencies on the build directory - copy them anywhere you like.

`utils\msvc-env.ps1` prefers `vcvarsall.bat` and assembles `INCLUDE`/`LIB`/`PATH` by hand when that script cannot provide a complete environment (for example when `reg.exe` is blocked by a security policy).

### Toolchain configuration (optional)

Nothing needs to be configured - every path is detected. To pin a specific toolchain, copy `utils\toolchain.ini.example` to either `utils\toolchain.ini` (local, ignored by git) or `%APPDATA%\awake\toolchain.ini` (shared by all checkouts) and uncomment what you need:

```ini
[visual-studio]
path = C:\Program Files\Microsoft Visual Studio\18\Community

[windows-sdk]
root = C:\Program Files (x86)\Windows Kits\10

[cmake]
path = C:\Program Files\CMake\bin\cmake.exe

[generator]
name = Visual Studio 18 2026

[sevenzip]
path = C:\Program Files\7-Zip\7z.exe
```

Priority: `AWAKE_TOOLCHAIN` environment variable (path to a file) > `utils\toolchain.ini` > `%APPDATA%\awake\toolchain.ini` > automatic detection. When a tool cannot be found, the build asks for its path once and writes the answer into the configuration file; in a non-interactive session it fails with the exact setting to add instead. The whole list of supported entries is documented inside `toolchain.ini.example`.

Steps that cannot be automated from a normal shell - colors, `powercfg /requests` verification, logon autostart, manual-sleep behavior - are printed as a manual checklist at the end.

For the release hardening pass (R16) three more tools exist:

- `utils/test/acceptance.py` - the three-tier acceptance orchestrator (`--tier auto|semi|manual|all`) producing `build/verification/report.md` and `results.json`. **The 1.0.0 gate: auto + semi green and the manual checklist signed off.**

- `utils/test/manual-checklist.md` - the formal manual review checklist (elevation matrix, real sleep/resume, logon autostart, clean-machine deployment, ...).

Unit tests live in `tests/` (Catch2, vendored in `tests/third_party/catch2`, so no network access is needed). They are built together with the executables and cover the parts that are hard to reach through the CLI - image name validation, the line helpers of the config parser, and the wire protocol including unknown-key tolerance:


## Usage

```
awake help              Show the help message.
awake version           Show the version.
awake 0                 Disable keep-awake (restore default power behavior).
awake 1                 Enable keep-awake (block idle sleep and hibernation).
awake 1 for <period>    Same, but released automatically after the period
                        (30m, 1h30m, 2h; units s/m/h/d).
awake 1 until <HH:MM>   Same, but released at that clock time (tomorrow when
                        the time has already passed - a warning is printed).
awake status            Show daemon, keep-awake, screen and watch list status
                        (never starts the daemon; watch list entries are green
                        when running, red when not).
awake list              List the watched applications (use --json for JSON).
awake screen on         Keep the screen on (blocks screen off, screensaver and idle lock).
awake screen on for <period>  Same, but released automatically after the period.
awake screen off        Stop keeping the screen on.
awake daemon on         Start the background daemon.
awake daemon off        Stop the background daemon.
awake daemon enable     Start the daemon automatically at logon (per-user registry Run key).
awake daemon disable    Do not start the daemon automatically at logon.
awake log               Show or change daemon logging (on / off / level /
                        max-files / max-size / export [path]).
awake reload            Re-read the configuration file immediately.
awake reset             Reset the configuration file (asks for confirmation).
awake add <imagename>   Add an image name to the watch list.
awake del <imagename>   Remove an image name from the watch list.
awake aliases           Show every command alias (also: awake a / awake alias).
```

Command aliases: `awake ?` and `awake h` are equivalent to `awake help`; `awake off`, `disable`, `stop` are equivalent to `awake 0`; `awake on`, `enable`, `start` are equivalent to `awake 1`; `awake st` is equivalent to `awake status`; `awake scr` is equivalent to `awake screen`; `awake screen 1` / `screen 0` are equivalent to `screen on` / `screen off`; `awake d` is equivalent to `awake daemon`; `awake daemon 1` / `daemon start` are equivalent to `daemon on`; `awake daemon 0` / `daemon stop` are equivalent to `daemon off`.

`awake aliases` prints the same mapping as an aligned table at any time (the help message shows it in its own "Command aliases" section).

Two output details worth knowing:

- the version banner names the build it came from, e.g. `awake 0.6.0-beta (git 3e548a6)`. A `-dirty` suffix marks a build made from uncommitted changes, and a build outside a git checkout reports the version alone.
- every interactive run ends with a one-line AI-generated-software reminder written to **stderr**. Redirecting or piping the output therefore stays clean, and `AWAKE_AI_NOTICE=always` / `=never` overrides the automatic decision.

Notes:

- `awake 0` and `awake 1` start the daemon automatically if it is not running.
- The keep-awake state is kept in the daemon's memory only. After the daemon restarts it is inactive again - timed periods are not an exception: the daemon has no way to remember them.
- A timed keep-awake is measured with a monotonic clock, so changing the system time or crossing a daylight saving boundary does not move the expiry point.
- When the daemon starts it sends a one-shot stay-awake notification to the system (resets the idle timer once), regardless of the current setting.
- The first run prints the Apache License 2.0 and asks for acceptance; `help` and `version` work without accepting. The answer is stored in `awake.ini`, so every file written by an older version asks once after the upgrade.
- The daemon refuses to run in an elevated console (its pipe would be uncontrollable from a normal shell) and `awake daemon on` fails with a clear error there. Automation environments whose runners are always elevated set `AWAKE_ALLOW_ELEVATED=1` to opt out; the daemon then prints a loud warning and `awake status` marks it with `(elevated)`.

## Configuration file

`awake.ini` lives next to `awake.exe` (portable). It is created automatically with a descriptive comment header when missing. Comments start with `#` or `;`; inside `[watch]` every other non-empty line is one image name, for example:

```ini
[license]
license_accepted = true

[watch]
notepad.exe
```

`license_accepted` records the first-run agreement: any value other than `true`, a missing entry, a missing file or a damaged file makes `awake` print the license again. Sections other than `[watch]` hold `key = value` settings and are never treated as watch entries.

While any listed image name is running, the daemon blocks idle sleep/hibernation. Use `awake add` / `awake del` to edit the list comfortably; changes are picked up automatically within 30 seconds, or immediately with `awake reload`. To discard all entries and restore the initial template, run `awake reset` - it warns you and asks for a second confirmation before overwriting the file, and a running daemon reloads the configuration right away (note that this also clears `license_accepted`).

## How it works

```
+-------------------+       named pipe           +----------------------------+
| awake.exe         |  \\.\pipe\awake_daemon     | awake.daemon.exe           |
| (client)          |  ------------------------> | (daemon)                   |
|  main (dispatch)  |  line-based ASCII          |  main (startup/teardown)   |
|  commands         |  request/response          |  server (pipe loop)        |
|  status           |                            |  state (shared flags)      |
|  autostart        |                            |  power (30 s poll thread)  |
|  log export       |                            |  monitor (power events)    |
|  logging          |                            |  logging (per-day files)   |
+-------------------+                            +----------------------------+
                                                                 |
                                                                 v
                                                SetThreadExecutionState
                                                    Windows power manager
```

- The daemon holds the Windows execution state `ES_CONTINUOUS | ES_SYSTEM_REQUIRED` via `SetThreadExecutionState`, which blocks idle sleep/hibernation without intercepting manual sleep requests.
- A dedicated "power thread" owns all execution state calls, applies changes on demand and at least every 30 seconds, and resets the state before the daemon exits.
- A hidden window on its own thread receives the system's suspend/resume broadcasts: after the machine wakes up, the execution state is re-applied immediately and the resume time is reported by `awake status`.
- Client and daemon communicate over the named pipe `\\.\pipe\awake_daemon` using a small line-based ASCII protocol. A mutex guarantees a single daemon instance.
- The daemon refuses to run unless launched by the client with a hidden `--internal-daemon <token>` option, so it cannot be started accidentally from the command line.
